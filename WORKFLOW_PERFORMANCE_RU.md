## Что ускорено в коде

1. **Архивы:** `gh api --paginate --slurp .../actions/artifacts?name=zone-engine-retention-archive` обрабатывает все страницы артефактов; после сортировки workflow проверяет metadata кандидатов и пробует скачать до трёх самых новых подходящих архивов. На старом логе пустой поиск занимал около 36 секунд. В предоставленном новом логе подходящий архив не найден, поэтому скорость и пагинация на фактических кандидатах не измерены.
2. **BingX protection:** если успешный `openOrders` снимок уже содержит валидный неизменённый SL, не делается второй идентичный read. Если SL создан или очищен, повторный запрос обязателен. На данном логе это около 10 секунд на каждую reconciliation phase (примерно 20 секунд суммарно для pre-scan и final); требуется новый runtime замер.
3. **Research 5m bars:** недостающие HTTP fetches выполняются параллельно с максимумом 2 workers; запись в persistent journal по-прежнему остаётся последовательной. На старом логе 201 Binance kline fetch занимал 24.86 секунд суммарного HTTP-времени; ожидается сокращение ожидания, но оно зависит от сетевой латентности и rate limiting.

Суммарный ожидаемый выигрыш — порядка **50–70 секунд**, но это гипотеза на основе измеренных задержек/кода, а не гарантированное время. Её надо подтвердить следующим workflow запуском.

## Что намеренно не ослаблялось

- Не снижалось число сканируемых инструментов или `SCAN_WORKERS=12`.
- Не пропускалось сопровождение активных позиций и проверка защитных ордеров.
- Не параллелизована запись журналов и не менялись зоны, направления LONG/SHORT либо правила открытия сделок.
- В live workflow остаётся `data/` для runtime-состояния; не удалять эту папку, пока переход к внешнему постоянному storage не реализован и не проверен.

## Отдельная долгосрочная причина

Checkout/fetch (~24 с) и commit/push (~14 с) во многом связаны с тем, что workflow хранит runtime JSONL в репозитории. Удалить `data/` только из source ZIP — не то же самое, что вывести runtime state из Git. Для более крупного сокращения потребуется миграция на постоянное хранилище с атомарной записью, backup/versioning и безопасным восстановлением active positions, order IDs, execution claims, cursors и журналов. Эту опасную миграцию не смешивали с оптимизациями текущего торгового цикла.

## Оптимизация 5.48.13: предварительный результат

Тяжёлая часть `research_forward.py` делала одну и ту же нормализацию исторических свечей и ATR-подготовку многократно для разных observations, а `_load_bars()` выставляет один и тот же DataFrame и под provider-specific key, и под symbol-only alias. 5.48.13 кеширует производные структуры только в рамках одного запуска: одна `_BarIndex` на identity исходного DataFrame и один prepared counterfactual frame на уникальную историю. Данные разных providers не объединяются; сами source bars не меняются.

Независимый differential benchmark сравнил **полные вложенные выходные словари** предыдущей и оптимизированной реализации, не только сводный PnL:

- synthetic 100 observations × 1 200 bars: 16.797 s → 1.006 s (~16.7× быстрее для counterfactual loop); 0 отличий результата;
- actual bootstrap series, 100 observations × 1 286 bars: 5.401 s → 0.821 s (~6.6× быстрее для counterfactual loop); 0 отличий результата;
- весь packaged seed: 656 alias keys сводились к 328 уникальным индексам; 141 478 bar rows; построение индексов ~0.503 s, подготовка один раз на уникальную историю ~0.941 s (~1.444 s вместе в этом локальном измерении).

Это локальные benchmark-и, не production-run. Основной ожидаемый выигрыш — уменьшение `RESEARCH_FORWARD_CALC`; `RESEARCH_FORWARD_INDEX` теперь отдельно логирует подготовку и её цену. Следующий Actions-run должен быть принят только после сравнения `RESEARCH_FORWARD_INDEX` + `RESEARCH_FORWARD_CALC` + количества `ready`, `matured_outcomes`, предупреждений и ошибок с базовым логом.
